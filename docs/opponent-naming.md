# 对手名称模式（正常 / 预设昵称 / 自定义）

## 使用

游戏顶部菜单「控制」页和管理器悬浮窗「控制」页各有一张「对手名称」卡，两处操作同一个设置：

| 模式 | 效果 |
| --- | --- |
| 正常（默认） | 保留服务器昵称，`showServer` 仍给每个座位加区服前缀。 |
| 预设昵称 | 三家对手按视觉从左到右显示为 `领头的羊`、`镇山的虎`、`远见的鹰`。 |
| 自定义 | 使用三个用户填写的名称；某一格留空则该座位保留服务器昵称。 |

「预设昵称」的存储值仍是 `abc`（也接受 `anonymize` 等旧写法），因此旧版本写下的设置、以及管理器侧 `OpponentNamingMode.ABC` 的 wire 值都不需要迁移；只有界面文案从「ABC 匿名」改成了「预设昵称」。

座位顺序：左家（上家）、对家、右家（下家）。三麻没有对家，两个对手按同一规则占据「左」「右」两格，中间那格不使用。

## 区服前缀与 `showServer`（独立开关）

`showServer` 是区服前缀（`[CN]`、`[JP]`、`[EN]`、`[??]`，中文标签带游戏自己的 U+FEFF）的**唯一决定因素**，与模式无关：

- 开：对手显示 `区服前缀 + 名称`，名称是预设昵称、自定义名称还是服务器原名都一样。
- 关：任何座位都不带前缀，改名后也不带。

改名只替换「名称」部分，绝不摘掉、改写或复制前缀：前缀由座位自己的账号 id 决定（账号 id 为 0 的机器人没有区服，永远不加）。两条路径用的是同一个 `zone_tag` 映射——协议层在 Rust 里，显示层通过 `majmax_naming_prefix` 这个 C ABI 现问现取，**不会**从名称或自定义标签的文本里用正则猜前缀（一个写着 `[JP]某个名字` 的自定义标签会被原样显示为 `[CN][JP]某个名字`，不会被当成前缀）。

当前牌桌（Lua 显示层）上，开关的三种情形：

| 情形 | 显示 |
| --- | --- |
| 被改名的座位（预设/自定义） | `开关 ? 前缀 : ""` + 标签 |
| 恢复正常、但这一桌当初被改过名（有原名缓存） | `开关 ? 前缀 : ""` + 缓存里的原名 |
| 这一桌根本没改名（正常模式，无缓存） | 游戏自己画的名字；开关**关**时只摘掉该座位自己那一个前缀，开关**开**时不做任何事（不凭空造前缀，否则会给机器人或本来没前缀的名字加上区服） |

也就是说：关掉开关时，当前牌桌立刻不再显示前缀；重新打开时，改过名的座位立刻带回来，没改过名的座位要等下一局（协议层只在那时写一次）。

**修改立即生效**：改动落到共享设置后，游戏内的 Lua 显示层会重画当前牌桌一次，画面上的名字当场变化。不需要重启游戏或重启模块，也不会重排、重连或改写任何请求。

## 两条生效路径（同一次读取的设置）

1. **当前牌桌（立即）**：`ui/MajsoulMaxNaming.lua` 包装 `DesktopMgr:get_player_name`——牌桌每个座位显示名字都走这个取值函数——并在共享设置变化时调用一次 `UI_DesktopInfo.Inst:RefreshSeat(true)` 重画。这是纯显示层的本地重绘，跑在 Unity 主线程上（由既有的 `LuaLooper.Update` 泵驱动，和自动切牌同一个 tick），不涉及网络、协议或服务器数据。
2. **下一局（数据层兜底）**：`authGame` 响应到达时，Rust 侧仍然按同一设置改写对手昵称。这样即使显示层没能挂钩（例如游戏版本变化导致本地 Lua 挂钩失效），下一局仍然按设置显示；它同时也是当前牌桌之外所有读取该响应的位置的兜底。

两条路径读同一份设置，不会出现两种结果：显示层始终以自己算出的标签覆盖对手座位，因此即使协议层已经改写、标签顺序有差异，看得到的仍然是同一组标签。

## 座位映射（不猜屏幕几何）

映射全部来自游戏自己的 `DesktopMgr:seat2LocalPosition`：本地座位是 1，位置数字朝「上家」方向递增。把对手按位置**降序**排列即得 `[左家(位置4), 对家(位置3), 右家(位置2)]`；三麻里游戏本身只存在两个对手位（位置 2、3），降序后同样是 `[左家, 右家]`，因此不需要假设三麻的屏幕坐标，也不做 `% 3` 之类的取模推算。`seat2LocalPosition` 返回 0（座位不存在/无法定位）的座位一律不改名，本地座位（`self.seat`）永远不参与替换。

## 恢复正常时为什么能拿回原名

协议层改写之后，客户端手里只剩预设昵称/自定义名称——当前牌桌已经不可能再读到服务器原名。Rust 侧因此为每次 `authGame` 记录一份**原名缓存**：改写前把将被替换的昵称按账号 id 存下来（最多 3 条，整份缓存随每次 `authGame` 替换，连接断开即清空）。选回「正常」时，显示层对每个对手座位先用缓存里的原名，缓存没有（该座位本来就没被改写，或对手是账号 id 为 0 的机器人）才回落到游戏原本的取值函数。

缓存里存的是**去掉区服前缀之后的原名**：协议层加过的那一段会被精确摘掉（只摘这个账号自己的那个标签，且只在 `showServer` 为开、也就是确实由自己加上去的时候摘），显示层再按**当前**的 `showServer` 状态拼回去。这样开关关了不会留着旧前缀，再打开也不会变成两段前缀。

缓存只活在一次 `authGame` 之内，因此不会把上一桌的名字带到这一桌；它也是纯显示数据，不写日志。

## 跨进程数据流

三处必须一致，且只有一个写入方：

1. `manager/OpponentNaming.kt`（管理进程）是唯一存储：`SharedPreferences("opponent-naming")` 的 `mode` + `names`。它只写这两个键，不碰任何其他偏好。
2. 游戏内顶部菜单通过 UID 校验的 `AiEndpointProvider` 写入（`namingSet`，缺省字段表示“保持不变”），回复是完整状态包，所以卡片永远显示“真正存下来的值”。悬浮窗本身在管理进程内，直接读写同一份存储。
3. 游戏进程 `ProbeModule` 在既有的 250 ms endpoint 轮询里每秒读一次 `namingGet`，值变化时调用 `nativeApplyNaming`（`probe.cpp`）→ `majmax_modder_update_settings`，Rust 侧解析、校验、原子落盘并替换内存快照。

Rust 侧随后把最新选择发布成一段紧凑状态（`majmax_naming_state`，格式 `mode\nshowServer\n左\n对\n右`，第二行 `1`/`0` 是 `showServer` 开关，空行表示该格保留原名）。Lua 侧每个 tick 读一次，**值变化**就是“用户刚改过”（只切开关也算一次改动），于是重画一次当前牌桌；重画只重试有限次（30 个 tick，约 3 秒），一次成功即停止，牌桌没打开时不会补画。Lua 只认这个五行格式：格式不符（例如只更新了一半的安装）就整体忽略，画面保持游戏原本的样子，宁可不改也不猜。

管线格式：

- provider 回给游戏进程：`{"mode":"normal|abc|custom","names":["","",""]}`
- 给 Rust 的补丁：`{"namingMode":"abc","customNames":["","",""]}`（camelCase，`SettingsPatch` 拒绝未知字段，因此补丁里只有这两个键）
- 给 Lua 的状态：`abc\n1\n领头的羊\n镇山的虎\n远见的鹰`（换行分隔；名称已禁止控制字符，所以无需转义）
- 给 Lua 的原名：`__majmax_naming_original(账号 id)`，返回**不带前缀**的服务器原名，没有可恢复的原名时返回空串
- 给 Lua 的区服标签：`__majmax_naming_prefix(账号 id)`，返回该账号的 `[CN]/[JP]/[EN]/[??]`，账号 id 为 0 时返回空串；Lua 侧按账号缓存（上限 128 条）

管理应用缺失或 URI 被撤销时不报错：模块保留已生效的值，和未解锁目录的策略一致。游戏进程每次启动后的第一次成功读取一定会写一次（即使是「正常」），这样管理器侧存储才是唯一事实来源。

## 实现要点

- 两处 UI 都沿用各自的既有刷新节奏：游戏内卡片由 `autoStatus` 轮询重绘，悬浮窗由服务 200 ms tick 重绘；都不新增定时器。
- 三段式选择器与输入框只在「自定义」时出现；输入框在**失去焦点**或点「保存名称」时保存，轮询不会覆盖仍有焦点的输入框（避免删掉正在输入的内容）。
- 保存名称同时切到「自定义」：名称只在自定义模式下才被使用。
- 语言：游戏内文案走 `helper/GameMenuText.kt` 的对照表（zh/en/ja，繁体由中文派生），悬浮窗走 `t(zh,en,ja)`；切换语言时两侧都会整体重绘。
- 显示层对每个座位的结果都包在 `pcall` 里：挂钩本身出错时直接调用未改动的原函数，和没装模块时完全一致；`get_player_name` 的第二个返回值（好友备注标记）对被改名的座位返回 `false`，对其他座位原样透传。

## 限制

- 显示层依赖游戏内的 Lua 注入（与设置页、自动切牌同一条链路）。它没能挂钩时当前牌桌不会变名，下一局仍由 `authGame` 改写生效。
- 改名只影响显示：请求载荷逐字节不变；本地座位（`self.seat`）永远不改名；座位不在 `player_datas` 里（观战等）时全部保留原名。
- 被改名座位的**好友备注**不再显示（备注是游戏在取值时按账号查的，显示层替换掉了整个返回值）；恢复正常后备注照常显示。本来就没被改写的座位保持备注。
- 前缀完全由 `showServer` 决定，与模式无关：开着时预设昵称/自定义名称同样带自己座位的区服标签，关掉时连服务器原名也不带。
- 打开开关不会给「这一桌本来就没前缀」的座位补前缀（那可能是机器人，或本来就没加过），它们下一局才会带上；关掉开关则立即摘掉。
- 账号 id 为 0 的机器人座位会被改名，但它没有区服，所以永远不加前缀；它也没有可恢复的原名，恢复正常后显示的是协议层留下的名字。
- 管理器进程被系统回收时，游戏进程会保留最后一次生效的模式；重新读到新值需要管理器进程重新起来（provider 调用会自动拉起）。
