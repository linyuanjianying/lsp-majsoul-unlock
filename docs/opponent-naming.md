# 对手名称模式（正常 / 预设昵称 / 自定义）

## 使用

游戏顶部菜单「控制」页和管理器悬浮窗「控制」页各有一张「对手名称」卡，两处操作同一个设置：

| 模式 | 效果 |
| --- | --- |
| 正常（默认） | 保留服务器昵称，`showServer` 仍给每个座位加区服前缀。 |
| 预设昵称 | 三家对手按视觉从左到右显示为 `领头的羊`、`镇山的虎`、`远见的鹰`。 |
| 自定义 | 使用三个用户填写的名称；某一格留空则该座位保留服务器昵称。 |

「预设昵称」的存储值仍是 `abc`（也接受 `anonymize` 等旧写法），因此旧版本写下的设置、以及管理器侧 `OpponentNamingMode.ABC` 的 wire 值都不需要迁移；只有界面文案从「ABC 匿名」改成了「预设昵称」。

座位顺序：左家（上家）、对家、右家（下家）。三麻没有对家，两个对手按同一规则占据「左」「右」两格，中间那格不使用；因此三麻只取**前两个**标签（预设的前两个名字、自定义的第 1、2 格），第 3 个标签在三麻里不参与显示。

「控制」页还有一个「变更后强制刷新牌桌」开关（默认开启；目前只有游戏内控制页有这个入口，悬浮窗卡片没有这一行，但 provider 的 `namingSet` 已经接受 `forceRefresh` 字段）。它只决定**设置值变了、而当前牌桌没有任何座位需要改写**时要不要顺手重画一次：真的往座位数据里写入了不同名字的变化一定会重画，与这个开关无关；关掉它之后，这类「只切了开关、数据没变」的改动要等下一个重绘点（下一局、换座位、结算页）才看得到。

## 区服前缀与 `showServer`（独立开关）

`showServer` 是区服前缀（`[CN]`、`[JP]`、`[EN]`、`[??]`，中文标签带游戏自己的 U+FEFF）的**唯一决定因素**，与模式无关：

- 开：对手显示 `区服前缀 + 名称`，名称是预设昵称、自定义名称还是服务器原名都一样。
- 关：任何座位都不带前缀，改名后也不带。

改名只替换「名称」部分，绝不摘掉、改写或复制前缀：前缀由座位自己的账号 id 决定（账号 id 为 0 的机器人没有区服，永远不加）。两条路径用的是同一个 `zone_tag` 映射——协议层在 Rust 里，显示层通过 `majmax_naming_prefix` 这个 C ABI 现问现取，**不会**从名称或自定义标签的文本里用正则猜前缀（一个写着 `[JP]某个名字` 的自定义标签会被原样显示为 `[CN][JP]某个名字`，不会被当成前缀）。

当前牌桌（Lua 显示层）上，开关的三种情形：

| 情形 | 显示 |
| --- | --- |
| 被改名的座位（预设/自定义） | `开关 ? 前缀 : ""` + 标签 |
| 恢复正常、但这一桌当初被改过名（Rust 原名缓存或 Lua 本地记录里有原值） | `开关 ? 前缀 : ""` + 那个原值 |
| 这一桌根本没改名（正常模式，无缓存） | 游戏自己画的名字；开关**关**时只摘掉该座位自己那一个前缀，开关**开**时不做任何事（不凭空造前缀，否则会给机器人或本来没前缀的名字加上区服） |

也就是说：关掉开关时，当前牌桌立刻不再显示前缀；重新打开时，改过名的座位立刻带回来，没改过名的座位要等下一局（协议层只在那时写一次）。

**修改立即生效**：改动落到共享设置后，游戏内的 Lua 显示层会改写当前牌桌的座位数据，并调用一次座位重画。不需要重启游戏或重启模块，也不会重排、重连或改写任何请求。至于「重画一次就等于画面上当场变化」，目前仍是待真机确认的一步，见下面的「未取得的证据」。

## 两条生效路径（同一次读取的设置）

1. **当前牌桌（立即）**：`ui/MajsoulMaxNaming.lua` 直接把当前牌桌对手座位的 `DesktopMgr.Inst.player_datas[seat].nickname` 换成目标名字——这正是客户端自己画座位名的数据源（结算页 `UI_GameEnd` 用 `container_name:SetName(DesktopMgr.Inst.player_datas[seat].nickname, …)` 画每一张卡片），换完再调用一次 `UI_DesktopInfo.Inst:RefreshSeat(true)` 让牌桌按新数据重画一次。客户端自己的匿名昵称模式走的也是这条链（写这个字段 + `RefreshSeat()`），区别是它还会调 `InitRoom()`——本模块**不**调，那是每桌一次的房间初始化，牌局中间重跑会重置牌局界面。这是纯显示层的本地改写，跑在 Unity 主线程上（由既有的 `LuaLooper.Update` 泵驱动，和自动切牌同一个 tick，约 100 ms），不涉及网络、协议或服务器数据。
   - **每 tick 幂等维护**：数据已经是目标值时不写、不重画，代价接近于零；新一局客户端按 `player_datas_temp` 重建座位名之后，下一个 tick 会自动补回目标值，不需要用户再动一次设置。
   - **`get_player_name` 只做一致性**：它仍被包装，但牌桌标签本身不经过它（它是带屏蔽词、隐藏昵称、好友备注的过滤取值路径，客户端画牌桌时不走这里）。包装只为让读这个函数的调用方看到与牌桌相同的名字；被改过名的座位返回 `(名字, false)`，其余座位原样透传。只包这个取值函数的老版本能装上却改不了一个字，原因就在这里。
   - **座位不再是对手时写回**：四麻变三麻、或 `ChangeMainBody` 把主视角换到某个座位后，该座位会被恢复成它被替换前的那个值。
2. **下一局（数据层兜底）**：`authGame` 响应到达时，Rust 侧仍然按同一设置改写对手昵称。这样即使显示层没能挂钩（例如游戏版本变化导致本地 Lua 挂钩失效），下一局仍然按设置显示；它同时也是当前牌桌之外所有读取该响应的位置的兜底。

两条路径读同一份设置，不会出现两种结果：显示层始终以自己算出的标签覆盖对手座位，因此即使协议层已经改写、标签顺序有差异，看得到的仍然是同一组标签。

### 未取得的证据：`UI_DesktopInfo` 的实现

- 客户端 `UI_DesktopInfo` 那段脚本**不在**可用的反编译 dump 里（打包脚本是加密的），所以 `RefreshSeat` 的实现无法逐行核对。这是本模块唯一一处「按调用点推断」的地方，写在这里，免得被当成已核实的事实。
- 采用的实参 `true` 来自**真实调用点**：`DesktopMgr:ChangeMainBody` 与 `DesktopMgr:RefreshSeatOnNewRound` 在座位内容变化后都用 `RefreshSeat(true)` 重画座位，而牌桌座位名必须跟随座位内容，所以这个重画点覆盖名字。客户端自己的匿名昵称序列则是写字段 + 调 `InitRoom()` + `RefreshSeat()`。
- 若某个版本里座位标签并不由 `RefreshSeat` 重画，替换也不会丢：数据字段是客户端取名的唯一来源，名字会在下一个重绘点（下一局、换座位、结算页或下一次 `authGame`）落到画面上。因此「改了设置后画面当场变化」目前是**推断 + 假牌桌页的单元测试**结论，仍需真机在牌局进行中确认一次。

## 座位映射（不猜屏幕几何）

映射全部来自游戏自己的 `DesktopMgr:seat2LocalPosition`：本地座位是 1，位置数字朝「上家」方向递增。把对手按位置**降序**排列即得 `[左家(位置4), 对家(位置3), 右家(位置2)]`；三麻里游戏本身只存在两个对手位（位置 2、3），降序后同样是 `[左家, 右家]`，因此不需要假设三麻的屏幕坐标，也不做 `% 3` 之类的取模推算。`seat2LocalPosition` 返回 0（座位不存在/无法定位）的座位一律不改名，本地座位（`self.seat`）永远不参与替换。

## 恢复正常时为什么能拿回原名

协议层改写之后，客户端手里只剩预设昵称/自定义名称——当前牌桌已经不可能再读到服务器原名。Rust 侧因此为每次 `authGame` 记录一份**原名缓存**：改写前把将被替换的昵称按账号 id 存下来（最多 3 条，整份缓存随每次 `authGame` 替换，连接断开即清空）。

显示层还有自己的一份**本地记录**，按座位存在这一桌的 `player_datas` 表上：第一次改写某个座位之前先记下它当时的值，此后只有客户端自己把值换掉（当前值不再等于自己写进去的那个值）时才重新记。它补的是 Rust 缓存覆盖不到的情形——这一桌的响应根本没被改写（例如开局之后才改的设置）、对手是账号 id 为 0 的机器人、以及同一桌里在预设与自定义之间来回切换。座位不再是对手时，这份记录会被用来把名字写回原值，然后一起清掉；客户端重建了座位表（新一局）时整份记录作废。

所以选回「正常」或清空某一格时，显示层对每个对手座位按这个顺序取值：**Rust 原名缓存 → 本地记录 → 牌桌当前值**（当前值只在确实被自己加过前缀时摘掉那一个前缀，其余原样保留）。

缓存里存的是**去掉区服前缀之后的原名**：协议层加过的那一段会被精确摘掉（只摘这个账号自己的那个标签，且只在 `showServer` 为开、也就是确实由自己加上去的时候摘），显示层再按**当前**的 `showServer` 状态拼回去。这样开关关了不会留着旧前缀，再打开也不会变成两段前缀。

Rust 侧这份缓存只活在一次 `authGame` 之内，因此不会把上一桌的名字带到这一桌；Lua 的本地记录只活在这一桌的座位表上，座位表被换掉即作废。两者都是纯显示数据，不写日志。

## 跨进程数据流

三处必须一致，且只有一个写入方：

1. `manager/OpponentNaming.kt`（管理进程）是唯一存储：`SharedPreferences("opponent-naming")` 的 `mode` + `names` + `force_refresh`。它只写这三个键，不碰任何其他偏好。
2. 游戏内顶部菜单通过 UID 校验的 `AiEndpointProvider` 写入（`namingSet`，缺省字段表示“保持不变”），回复是完整状态包，所以卡片永远显示“真正存下来的值”。悬浮窗本身在管理进程内，直接读写同一份存储。
3. 游戏进程 `ProbeModule` 在既有的 250 ms endpoint 轮询里每秒读一次 `namingGet`，值变化时调用 `nativeApplyNaming`（`probe.cpp`）→ `majmax_modder_update_settings`，Rust 侧解析、校验、原子落盘并替换内存快照。

Rust 侧随后把最新选择发布成一段紧凑状态（`majmax_naming_state`，格式 `mode\nshowServer\n左\n对\n右\nforceRefresh`，第二行 `1`/`0` 是 `showServer` 开关，空行表示该格保留原名，第 6 行 `1`/`0` 是「变更后强制刷新牌桌」开关）。Lua 侧每个 tick 读一次，**值变化**就是“用户刚改过”（只切任一个开关也算一次改动）：有座位真的被写入时一定重画；没有座位需要写、但第 6 行是 `1` 时也补一次重画。重画只重试有限次（30 个 tick，约 3 秒），一次成功即停止，牌桌没打开时不会补画。

Lua 同时接受旧的**五行**格式（没有第 6 行）并把它当作 `forceRefresh=1`，这样「只更新了一半的安装」（新 Lua + 旧原生侧，或反过来）仍然能立即改名；其他形状（行数不对、内容为空）整体忽略，画面保持游戏原本的样子，宁可不改也不猜。

管线格式：

- provider 回给游戏进程：`{"mode":"normal|abc|custom","names":["","",""],"forceRefresh":true}`
- 给 Rust 的补丁：`{"namingMode":"abc","customNames":["","",""],"namingForceRefresh":true}`（camelCase，`SettingsPatch` 拒绝未知字段，因此补丁里只有这三个键）
- 给 Lua 的状态：`abc\n1\n领头的羊\n镇山的虎\n远见的鹰\n1`（换行分隔；名称已禁止控制字符，所以无需转义）
- 给 Lua 的原名：`__majmax_naming_original(账号 id)`，返回**不带前缀**的服务器原名，没有可恢复的原名时返回空串
- 给 Lua 的区服标签：`__majmax_naming_prefix(账号 id)`，返回该账号的 `[CN]/[JP]/[EN]/[??]`，账号 id 为 0 时返回空串；Lua 侧按账号缓存（上限 128 条）

管理应用缺失或 URI 被撤销时不报错：模块保留已生效的值，和未解锁目录的策略一致。游戏进程每次启动后的第一次成功读取一定会写一次（即使是「正常」），这样管理器侧存储才是唯一事实来源。

## 实现要点

- 两处 UI 都沿用各自的既有刷新节奏：游戏内卡片由 `autoStatus` 轮询重绘，悬浮窗由服务 200 ms tick 重绘；都不新增定时器。
- 三段式选择器与输入框只在「自定义」时出现；输入框在**失去焦点**或点「保存名称」时保存，轮询不会覆盖仍有焦点的输入框（避免删掉正在输入的内容）。
- 保存名称同时切到「自定义」：名称只在自定义模式下才被使用。
- 语言：游戏内文案走 `helper/GameMenuText.kt` 的对照表（zh/en/ja，繁体由中文派生），悬浮窗走 `t(zh,en,ja)`；切换语言时两侧都会整体重绘。
- 改名不依赖 `get_player_name`：它写的是座位数据的 `nickname`。该取值函数被包装只是为了**一致**——被改过名的座位从它读到同一个名字（第二个返回值好友备注标记为 `false`），其他座位原样透传；牌桌标签本身不走它。
- 每一步都在 `pcall` 里：取值函数出错时直接调用未改动的原函数（和没装模块时完全一致），重画出错或 `UI_DesktopInfo` 不存在时只当作一次失败，不会抛到游戏里，也不会无限重试（上限 30 个 tick）。

## 限制

- 显示层依赖游戏内的 Lua 注入（与设置页、自动切牌同一条链路）。它没能挂钩时当前牌桌不会变名，下一局仍由 `authGame` 改写生效。
- 改名只影响显示：请求载荷逐字节不变；本地座位（`self.seat`）永远不改名；座位不在 `player_datas` 里（观战等）时全部保留原名。
- 被改名座位从 `get_player_name` 读到的**好友备注**不再显示（本模块对该座位直接返回 `(名字, false)`，备注是游戏在该取值路径里按账号查的）；恢复正常后备注照常显示。本来就没被改写的座位保持备注。
- 前缀完全由 `showServer` 决定，与模式无关：开着时预设昵称/自定义名称同样带自己座位的区服标签，关掉时连服务器原名也不带。
- 打开开关不会给「这一桌本来就没前缀」的座位补前缀（那可能是机器人，或本来就没加过），它们下一局才会带上；关掉开关则立即摘掉。
- 账号 id 为 0 的机器人座位会被改名，但它没有区服，所以永远不加前缀；它也没有可恢复的原名，恢复正常后显示的是协议层留下的名字。
- 管理器进程被系统回收时，游戏进程会保留最后一次生效的模式；重新读到新值需要管理器进程重新起来（provider 调用会自动拉起）。
- 「改了设置后画面当场变化」这一步还没有真机证据：客户端 `UI_DesktopInfo` 的脚本是加密打包的，拿不到源码，`RefreshSeat(true)` 的实参来自 `DesktopMgr:ChangeMainBody` / `RefreshSeatOnNewRound` 这些真实调用点，而不是读到的实现细节。若某个版本不重画座位标签，名字会等到下一个重绘点才出现（数据已经换好了）。
- 关掉「变更后强制刷新牌桌」后，只有真的往座位数据写入了不同名字的变化才会重画；像「只切 `showServer`、数据本身没变」这种改动虽然已经生效，但要等下一个重绘点才看得到——这正是这个开关存在的意义，默认开着。
